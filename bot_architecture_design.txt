# Meeff Bot Architecture Design Document

## The Goal
To create a maintainable, extensible, and testable architecture for an Android UI automation bot. 
Upcoming features require the bot to:
1. Extract photos and send them to an AI for decision-making.
2. Continuously determine the current state of the app (Swiping, Chatting, Ad, Popup).
3. Engage in automated chatting.
4. Be fully unit-testable.

**Golden Rule:** Keep it as simple as possible, but powerful enough to handle the complex requirements.

---

## Design Idea 1: The Monolithic "God Object" (Procedural)
All logic is contained within a single massive `MeeffBot` class. 
- Methods like `tap_like()`, `check_if_ad_is_showing()`, `extract_photo_and_send_to_ai()`, and `send_chat_message()` all live in one file and share the same class state.

**Pros:**
- Extremely easy to write initially. 
- Zero boilerplate code.
- Simple conceptual model for a beginner.

**Cons:**
- **Fails the extensibility test:** As we add chat and AI, this file will quickly become a 2000+ line unmaintainable mess.
- **Fails the testability test:** You cannot easily unit test the "AI decision" logic without also firing up the ADB connection, because they are deeply coupled in the same class.

---

## Design Idea 2: Strict Finite State Machine (FSM)
The bot is modeled as a strict State Machine. The app is always in exactly one state: `SwipeScreenState`, `ChatScreenState`, `AdShowingState`. 
- Every state is its own class containing an `execute()` method. 
- For example, if the bot detects an ad, it transitions to `AdShowingState`, which has the sole responsibility of finding the "X" button and transitioning back to `SwipeScreenState`.

**Pros:**
- **Extremely robust:** It perfectly models how a UI actually works. You can't accidentally try to "Swipe Right" if the bot knows it is currently in the `ChatScreenState`.
- **Excellent for popups:** Ad handling becomes just another state transition.

**Cons:**
- **High Complexity:** It violates the Golden Rule of simplicity. Implementing a formal FSM pattern in Python requires significant boilerplate. Passing data between states (e.g., passing the AI's decision from the `AnalyzingState` to the `SwipingState`) can become convoluted.

---

## Design Idea 3: Component-Based Architecture (Service Pattern)
We break the bot down into modular, single-responsibility "Services" managed by a central `Controller` loop.

1. **`AdbService`**: Strictly handles communication with the phone (tapping, dumping UI, launching apps). Knows nothing about Meeff.
2. **`VisionService`**: Uses `AdbService` to get the screen state (XML or screenshot) and parses it. It answers questions like: "Is there an ad?", "Where is the Like button?", "Extract the profile photo."
3. **`BrainService` (AI)**: Takes the photo from `VisionService` and returns a boolean (Like/Pass).
4. **`ChatService`**: Handles messaging logic.
5. **`BotController`**: The main loop. It uses `VisionService` to figure out what's on screen, then routes the action to the correct service.

**Pros:**
- **Highly Modular:** Adding a new feature just means adding a new Service. 
- **Extremely Testable:** We can unit test the `BrainService` (AI) perfectly by just passing it a fake image file. We can mock the `AdbService` so tests run instantly without a phone connected.
- **Balanced Simplicity:** It avoids the strict boilerplate of an FSM, but prevents the spaghetti code of the God Object. 

**Cons:**
- Requires slightly more files and setup than Design 1.

---

## Final Critique & Decision

**Selected Architecture: Design 3 (Component-Based Architecture)**

*Why?*
Design 3 hits the sweet spot. 

Design 1 (Monolith) is a trap; it seems simple now but will make adding the AI and Chat features a nightmare, and unit testing impossible. 
Design 2 (FSM) is academically pure but over-engineered for a script primarily doing sequential UI actions. 

**Design 3 (Component-Based)** gives us the power we need. By separating the "Eyes" (`VisionService`), the "Hands" (`AdbService`), and the "Brain" (`BotController` / AI), we can easily unit test everything. If we want to change from parsing XML to using OpenCV for image recognition later, we only rewrite the `VisionService`—the rest of the bot doesn't even know it happened. 

This design adheres to the Golden Rule: It is simple enough to understand at a glance, but powerful enough to support complex AI integrations and mocking for unit tests.
